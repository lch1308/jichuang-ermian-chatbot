# COC 7 跑团平台与升级方案：审核稿

调研日期：2026-10-22。状态：方案，尚未实施。

已确认：以《克苏鲁的呼唤》第七版（COC 7）为基线；具体模组以后选择；优先免费开源，付费方案仅作对照。

后续确认的测试顺序：先由真人 KP 主持，验证双 AI 调查员与平台闭环；完成后再接入 AI KP 测试。该确认不等于已经授权安装或迁移平台。

界面要求补充：保留地图和 Live2D 两套功能，将它们整合在同一个应用窗口中；不要求用户管理两个并排的独立窗口。此要求不意味着更换平台或重写两套功能。

本轮依据桌面的《升级清单》、此前的跑团讨论稿及后续需求重新选型。没有安装软件、修改现有插件、迁移存档、启动服务或调用收费模型。文中“拟做”“验收”均指后续工作，不能当成已完成的能力。

## 1. 建议你先审核的结论

**建议以“MapTool 桌面平台＋自托管 BCDice 检定服务＋双 MaiBot 连接层＋Live2D 舞台”为免费路线，先做一轮接入验证，再决定正式迁移。**

这条路线的分工很直观：MapTool 管地图、棋子、视野和主持权限；BCDice 实际掷骰并处理已有的 COC 7 检定；故机与鱼宝负责扮演调查员、讨论和提出行动；你们负责主持与裁决。连接层将这些结果组织成同一局游戏，并记录真实发生的行为。

**它不是现成的一体化 COC 产品。** 免费路线需要我们补角色卡与状态接入、AI 发言协调、记忆权限和 Live2D 联动。“地图和双 Live2D 在同一个桌面窗口中”现为界面目标，优先验证 MapTool 内的可停靠网页面板能否承载现有舞台，不能承诺安装后自然获得。

如果你的优先级变成“尽量少开发，直接获得更完整的 COC 规则自动化”，Foundry＋CoC7 系统值得重新考虑；它目前作为付费参照。两种选择的区别主要是开发工作与现成自动化之间的取舍。

## 2. 我们实际需要保留什么

| 需求 | 本方案中的安排 |
| --- | --- |
| 两个真人都可以主持 | 独立主持账号，双方具备房间管理和裁决权限；冲突裁决由程序检测 |
| 两个 MaiBot 当玩家 | 各自电脑运行原有模型，通过插件连接同一战役 |
| 自主讨论与行动 | 主持介绍结束后，机器人可讨论、提问、提出行动，并等待裁决 |
| 不打断主持人和同伴 | 房间统一协调发言；后台观察和前台说话分开 |
| 跑团独立记忆 | 按战役、分支、角色隔离，默认不读写 QQ 和日常 Live2D 记忆 |
| 双 Live2D、表情、气泡 | 保留现有资源，新增实际播放回执与角色上方对话气泡 |
| 语音开关与较快反馈 | 主持控制房间语音，各角色单独开关；先显示处理状态，再生成文本与语音 |
| 有限世界线、可编辑 | 主持编辑地点、线索、NPC、阶段条件和结局；开局锁定版本 |
| 地图移动与场景拓展 | 先支持棋子移动和经主持批准的地点扩展；不承诺自动生成可探索 3D 世界 |
| 日志可读、可复盘 | 按一轮行动汇总，区分公开记录与主持机密记录 |

原始讨论稿中的轻量 d20，以及后来其他规则的角色属性，不直接换算成 COC 7。保留人物性格与背景素材，重新审核调查员卡。

### 3.1 MapTool 的优势与必须面对的问题

它能复用成熟的地图、视野、棋子所有权和开服功能，也符合你倾向桌面使用的想法。支持多名 GM，可以给两位真人分别配置身份；严格棋子所有权、个人视野等设置需要在建房时正确启用。[开服权限](https://wiki.rptools.info/index.php/Introduction_to_Game_Hosting)、[玩家认证](https://wiki.rptools.info/index.php/Player_Databases)。

但不能把“支持 COC 框架”理解为“自带维护完善的 COC7 系统”。官方目录确实列有 Merudo 的七版框架，标注年份为 2019，并提醒旧框架可能无法正常用于现代版本。其当前兼容性和独立素材许可尚未确认，因此不把它作为默认依赖。[框架目录](https://wiki.rptools.info/index.php/Frameworks)。

本次查到的稳定发行版为 1.18.7。若以后实施，双方锁定同一个经验证版本；不在旧目录上直接覆盖解压，战役资料单独保存。[1.18.7 发布说明](https://github.com/RPTools/maptool/releases/tag/1.18.7)。

### 3.2 为什么默认考虑 BCDice，而不是同时装两个骰子

BCDice 的优势是接口明确：调用指定规则系统的 roll 接口，能够得到原始骰值、结果文本、成功／失败等标记。它比较适合“外部 MaiBot→连接服务→实际检定”的结构。[API 文档](https://github.com/bcdice/bcdice-api/blob/master/docs/api_v2.md)。

海豹骰已有中文人物卡指令、对抗、理智与成长等功能，适合人在聊天里跑团。但是“JS 插件能联网”不等于“已有完整 CoC7 JSON 服务”。其插件类型定义尚不能证明存在可直接执行任意完整检定并取得结构化结果的入口。采用它可能多出消息身份适配、输出捕获和结果规范化工作。[海豹 COC7 手册](https://docs.sealdice.com/use/coc7.html)、[插件类型定义](https://github.com/sealdice/sealdice-js-ext-template/blob/master/types/seal.d.ts)。

因此建议首轮只接一个权威检定引擎。BCDice 为默认候选；如果你们更希望直接在 QQ/KOOK 输入中文指令，并复用海豹人物卡，再改选海豹路线。不让两个引擎为同一行动各掷一次骰子。

### 3.3 免费路线不适合时如何调整

- **要求更完整的 COC 流程辅助**：重新审核 Foundry。现有 CoC7 系统覆盖更多角色卡、战斗、理智等流程，并有简繁中文，仍需 KP 作情境裁决。调研时包版本为 8.16，最低 Foundry 12、验证至 14；8.16 是最后支持 12 的版本，且 12 部分功能不完整，不能任意混搭版本。[系统仓库](https://github.com/Miskatonic-Investigative-Society/CoC7-FoundryVTT)、[版本说明](https://github.com/Miskatonic-Investigative-Society/CoC7-FoundryVTT/releases/tag/8.16)。平台当日标价为 50 美元，税费以购买时为准，未含额外内容。[购买页](https://foundryvtt.com/purchase/)。
- **若 MapTool 单窗口接入验证失败，且你同意调整平台**：再进一步验证 Udonarium。它与 Live2D 同属网页技术，界面整合更顺手；但不能假设隐藏一个按钮就保护了 KP 秘密，也不能忽略当前部署依赖。[原版项目](https://github.com/TK11235/udonarium)、[后端项目](https://github.com/TK11235/udonarium-backend)。
- **以后倾向 AI KP 主持真人**：深入审核 The Veil。它已有 HTTP／Socket.IO 文档，值得参考；当前资料仍不足以认定它能直接替代双 AI 玩家协调系统。[接口文档](https://github.com/Nobook1121/The-Veil/blob/main/docs/api.md)。

其他边界：Fantasy Grounds 现在的软件本身免费，不能继续套用过去的 Ultimate／Demo 购买说明；其 COC7 规则集仍需单独购买。[官方商品页](https://www.fantasygrounds.com/store/product.php?id=CHAFGCOCCOC7ERS)。Roll20 的 Mods 为 Pro 能力；CCFOLIA 的角色粘贴接口不等同于稳定的全房间控制 API。[Roll20 Mods](https://pages.roll20.net/mods)、[CCFOLIA 开发文档](https://docs.ccfolia.com/developer-api/clipboard-api)。

## 4. 推荐架构：分别负责，不重复保存三套真相

```text
你的电脑（拟作为主机）
  MapTool 房间：地图、棋子、视野
           ↕ 经授权的宏／扩展
  跑团连接服务：人物卡、已确认事件、任务、权限、审计
           ├── BCDice：真实骰点与已有规则检定
           ├── 故机的 PC 插件 ── 你的 MaiBot／记忆／语音适配
           ├── 鱼宝的 PC 插件 ── 同伴的 MaiBot／记忆／语音适配
           └── 双 Live2D 舞台：气泡、表情、文字、语音

你与同伴：各自使用主持身份连接；各自电脑加载两套获许可的模型资源
```

“跑团连接服务”是拟新增或从现有 StoryRoom 后端中抽取的服务，不是查到的第三方成品。旧 StoryRoom 的任务、记忆隔离和日志能力可以评估复用；前端可以替换，不要求继续使用原来的页面布局。

### 数据由谁说了算

| 数据 | 拟定的权威来源 | 其他位置的处理 |
| --- | --- | --- |
| HP、SAN、技能、物品、已经确认的故事事件 | 战役数据库，由授权操作提交 | MapTool 面板、舞台、AI 上下文是带版本的副本 |
| 地图坐标、视野、迷雾 | MapTool | 导出角色有权知道的位置／可见对象给连接服务 |
| 一次真实骰点 | 绑定行动编号的 BCDice 执行记录 | 展示相同结果，不因刷新再次掷骰 |
| 对外说了什么 | 房间批准发送的发言事件 | 本地模型草稿不算已发送内容 |
| 模型服务配置、个人语音服务密钥 | 各自电脑 | 平台无需收集双方全部 API 密钥 |

这是架构建议，角色卡存储和界面仍需开发，不算 BCDice 已有功能。MapTool 中的 HP/SAN 显示作为副本，不能与后台各自随意修改；主持修改必须经过明确的提交入口。地图涉及检定距离时，需要使用有版本的位置快照，不能依据过期坐标结算。

## 5. 连接方式与部署约束

沿用“你当主机、双方 MaiBot 留在各自电脑”的方向。主机拟运行 MapTool 房间、连接服务和检定服务；同伴连接房间并运行自己的 PC 插件。

但 MapTool 游戏连接与网页接口是两条通道，**旧网页的 8790 地址或 HTTP 转发地址不能直接当作 MapTool 联机地址**。正式实施时优先验证现有组网方式是否同时支持这两类连接；具体网络工具、端口和域名留待核实，不在本方案中凭空生成可用地址。

MapTool 的 REST 宏可以向外发送 HTTP 请求，且要求可信宏。它不等于 MapTool 自带可供外部程序随意控制的入站 REST 服务器。[REST.post 文档](https://wiki.rptools.info/index.php/REST.post)。

首版采用短请求：提交任务后立即返回任务编号，后续获取结果；不让一个宏一直等几十秒的 AI 生成。结果先在舞台显示，MapTool 通过“同步已批准状态”宏拉取。自动刷新／回写的可用扩展入口要单独验证；若只能靠频繁人工同步且影响体验，就不进入正式迁移。

两位真人分别使用自己的主持凭据，两台机器人分别使用自己的角色凭据。玩家密钥、主持密码、模型 API 密钥用途不同；交付包只放示例，不放本机有效密钥。

## 6. COC 7 规则：现成能力与开发边界

建议首版采用经典 COC7，是否加入 Pulp 或其他房规留空。规则来源、勘误、选项与引擎版本写入战役配置，开局锁定；变更需主持确认并记录。

BCDice 的 COC7 源码已有普通／困难／极难等成功等级、奖惩骰及若干规则命令。**其中 CBR 是组合检定，不能把它当成对抗检定。** 部分自动射击支持也不等于完整战斗结算。[COC7 实现](https://github.com/bcdice/BCDice/blob/master/lib/bcdice/game_system/Cthulhu7th.rb)。

| 能力 | 首个可玩版本拟提供 | 不应声称已经自动解决的部分 |
| --- | --- | --- |
| 属性／技能 d100 检定 | 读取批准人物卡、难度、奖惩骰，调用现成引擎 | 哪个技能适用、是否需要掷骰，由 KP 决定 |
| 成功等级 | 将引擎结果规范为稳定字段并展示原始骰值 | API 现有布尔字段不能当作完整等级枚举 |
| 对抗 | 双方真实检定，明确行动类型，提交比较与裁决 | 战斗反击、闪避等不同平手规则不能统一处理 |
| 孤注一掷 | 记录原检定、尝试理由、KP 许可和额外后果 | 不允许机器人把失败当网络问题反复重掷 |
| 幸运消耗 | 作为规则选项，合法时由授权方确认扣除 | 不默认对所有检定都允许使用 |
| SAN | 实际检定、损失表达式、损失前后记录 | 恐怖内容、损失范围、疯狂表现需 KP 确认 |
| HP、伤害、重伤 | 保存状态，记录实际伤害与人工裁决 | 不承诺完整战斗自动化、全部武器与特殊情况 |
| 技能成长 | 标记可成长项目，在指定阶段发起成长流程 | 不把每次成功直接换成技能加点 |
| 追逐、复杂射击、载具等 | 首版由 KP 手动处理，保留结构化记录 | 不列为首版已支持的完整规则 |

普通／困难／极难的适配不能仅靠正则匹配一段中文结果。优先由封装层提供稳定等级字段；如须根据原始骰值和参数规范化，应针对固定引擎版本进行边界验证，保留原始返回供复核。这是小范围接口适配，也需测试。

中文界面由我们的显示层负责。BCDice 上游另有 COC7 繁体实现，但不能假设任意发行包都内置简体中文、或不同语言实现完全一致；实施前锁定一个规则系统及版本，核对关键结果，再做显示翻译。[繁体实现](https://github.com/bcdice/BCDice/blob/master/lib/bcdice/game_system/Cthulhu7th_ChineseTraditional.rb)。

**SAN 是规则中的理智值，心情是角色的情绪状态，二者分别保存。** SAN 下降可能影响心情与表现，但“心情 80”不会自动意味着 SAN 为 80；开心也不能自动治疗理智损失。

如果选海豹，必须显式设置并记录规则选项；它区分规则书检定与房规检定，不能把“常用房规”默认宣传成原书规则。[海豹规则说明](https://docs.sealdice.com/use/coc7.html)。

## 7. 一轮游戏的实际体验

以下是设计示例，不是已经运行的测试，也没有替你们选模组。

1. 你们介绍：“调查员来到一间废弃办公室，桌上散落着文件。”点击“介绍结束，允许讨论”。
2. 故机与鱼宝收到公开描述和各自有权读取的记忆。故机可以询问同伴，鱼宝可以提出先检查窗户；不必每句话都由 KP 点名。
3. 房间安排一个角色说话，另一个继续观察。讨论没有新进展时停下来，等待主持或行动结果。
4. 故机提出：“我想查看文件，寻找最近来访者的记录。”这只是行动提案，还没有找到线索。
5. KP 决定是否需要检定、使用什么技能及难度。平台从正式角色卡读取数值，不接受模型临时编造一个“侦查 95”。
6. 引擎执行一次真实检定。示例：技能 70、骰点 23，对应困难成功；这两个数是说明用的模拟数据。
7. KP 依据预设线索和当前状态批准公开内容。检定成功不等于允许 AI 随意创造真相。
8. 系统保存实际事件，更新批准的角色状态、可见线索和经历。故机根据结果继续讨论，舞台展示对应表情。

这个闭环让“过去影响现在”有明确依据：后来角色再遇到同一个名字，会引用此前真正获知的记录，而不是凭模型续写出一段没发生过的剧情。

## 8. 双 AI 如何自由讨论，又不一直抢话

拟把“观察”“准备发言”“实际发言”分开：所有有权获得的房间事件持续进入观察队列；达到合适的讨论时机才请求角色模型；只有拿到发言许可才播放。

主持可以切换三种状态：介绍／裁决中、自由讨论、等待行动结果。主持说话时暂停机器人对外输出；同伴正在发言时，另一位可以准备，但不能抢占语音。讨论采用可配置的轮次或时长预算，已有结论、需要 KP 回答或没有新增信息时结束，不让两个机器人永远互相接话。

两位真人都能管理房间与裁决，但同一个行动只能提交一次最终结果。两人同时修改同一版本时，后提交者看到冲突提示，不能悄悄覆盖前者。

你们拥有完整主持权限，不表示机器人也拥有主持权限。故机不能冒用你的身份批准自己的成功；鱼宝也不能读取同伴主持账号能看到的全部秘密。

AI KP 作为后续独立的角色与模型接入。按已确认顺序，首轮由真人 KP 主持，不依赖 AI KP。连接层预留统一的主持操作：发布现场、批准检定、确认后果、公开线索、推进阶段。真人通过界面执行；后续 AI KP 提交相同类型的操作，并接受权限和规则校验。AI KP 与 AI 调查员不共用一份无限制上下文。

## 9. COC 最重要的兼容问题：秘密不能提前泄露

数据至少分为主持机密、房间公开信息、故机私人信息、鱼宝私人信息。

主持可以看完整模组和隐藏线索；某个调查员只能得到已经公开或单独告知它的内容。过滤必须发生在服务端，在发送给模型之前完成。不能先把完整模组发给玩家模型，再靠一句“请不要剧透”解决。

同样的隔离适用于记忆检索、日志、场景图片生成、暗骰结果和地图快照。若图片提示词中包含“墙后藏着真凶”，即使聊天过滤正确，也可能通过画面泄密。玩家舞台使用公开场景描述；主持私有素材单独保存。

真人可以知晓幕后内容，AI 角色仍然不知道。测试时专门安排一个只有 KP 知道的虚构口令，检查两个角色的请求上下文、检索结果和导出日志是否出现它。

## 10. 世界线与记忆怎么适配

### 可编辑的有限故事

COC 调查通常需要线索网络，而不只是固定顺序的关卡。拟提供地点、NPC、线索及公开条件、重要事件、时间推进、可接受结局的编辑入口。调查员可以采用不同顺序和办法；遇到边界外的提案，交给主持批准，而不是自动开启新世界。

| 可编辑内容 | 如何满足 Lv2.5 的要求 |
| --- | --- |
| 世界边界与人物过去 | 固定年代、地域、允许的超自然设定及调查员来历，角色不能临时改写 |
| 故事阶段 | 明确开局、调查、危机、收束等阶段，切换有事实或时间条件 |
| 有限分支 | 根据已公开线索、调查员选择、已确认事件进入不同路径 |
| 结局集合 | 你们事先设置或审核可接受的结局；结束后不自动创造下一条主线 |
| 经历的影响 | 保存事件如何改变信任、当前看法、心情或角色状态，后续决策能引用 |

这里限制的是故事空间和事实变更权限，不要求提前写好每句台词。新增地点或分支可以先作为草案交给主持编辑，批准并记录版本后再进入本局。

关键线索是否需要检定、失败后如何继续，由你们依据模组设计。不能把所有推进条件都绑在一次骰点成功上，导致两个机器人反复掷骰才能继续。

开局锁定剧本版本。主持中途修订时显示差异，明确对当前局何时生效。地图新地点、生成图片或 NPC 的一句猜测，都不自动变成世界事实。

### 隔离且可更新的记忆

复用记忆检索能力，按“战役＋分支＋角色”隔离，另加信息可见范围。默认不读取 QQ／日常 Live2D 用户画像，不将虚构跑团事件写入现实用户事实表。

经历区分“实际发生”“角色猜测”“尚未批准的计划”。比如“故机怀疑店员说谎”可以记住，但不能改写成“店员就是凶手”。每条重要事实关联来源事件，撤销裁决或回档后，旧分支的相关记忆停止参与当前检索，原始审计保留。

技能、HP、SAN 等当前数值直接读取正式角色卡。不能因为旧记忆里写着 SAN 60，就覆盖现在已经变成 55 的状态。

## 11. Live2D、语音与界面升级

### 显示安排

按最新要求，目标是一个应用窗口中同时显示地图、双 Live2D 和主持操作。两套功能仍分别工作，用户不需要来回切换独立窗口。舞台包含双模型上方的对话气泡、较大字号和对比度、完整聊天记录、当前说话者、处理中状态和角色状态卡。

优先验证将现有舞台接入 MapTool 可停靠的 HTML5 面板，地图占主要区域，侧边显示模型与对话，主持操作可折叠。MapTool 官方有布局入口，但 HTML5 支持不等于已经验证 Cubism／WebGL、音频及现有前端依赖均兼容。[frame5 文档](https://wiki.rptools.info/index.php/frame5)。

阶段 A 先测试双模型渲染、表情、口型、语音、地图鼠标操作、键盘焦点、窗口缩放和持续运行。若内嵌面板不适用，再评估桌面容器整合；跨进程窗口嵌入还需验证缩放与焦点等行为，不能当作现成保证。[Windows 窗口嵌入说明](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setparent)。更换平台另行讨论，不因单窗口需求自动决定。

### 表情与动作

各模型有独立资源清单与映射，沿用故机和鱼宝现有文件。表达“疑惑”时调用该模型确实存在的表情；没有对应资源时，明确降级到思考或默认状态，不伪造“已播放”。移动棋子、移动 Live2D 在舞台上的位置、播放行走动作是三件事；缺少行走资源时只能做位置变化。

日志区分请求发出、资源找到、前端启动成功和实际结束。网页加载失败时，保留文字交流，不让表情异常阻塞整轮跑团。

### 语音与反馈

房间主持控制“是否启用语音”；故机、鱼宝分别有 TTS 开关；每位观众可以本地静音。一个角色正在说话时，双方观众应能同时听见，不能把“房间只能一个角色说话”错误地做成“只有一台观众电脑能播放”。

保留双方现有语音服务，通过适配器连接，不要求同伴更换语音包。文字准备好即可展示和排队朗读，不能必须等整段合成完成才显示。首版可固定语音参数；心情影响语速、语调作为可选兼容能力，不让它阻塞基本交流。

以系统接受一次输入为起点，拟要求 10 秒内出现实际可见的状态或表情反馈；最终回答与语音时延分别统计，不能用“后台写了一条处理中日志”冒充用户已感知的反馈。

语音临时识别结果只用于可取消的准备工作。涉及投骰、扣除状态、移动到新地点和公开线索的操作，要依据确认输入和授权执行。此前已经回退的个人 Live2D 延迟补丁，不因这次升级自动恢复。

### 场景生成

先支持背景导入、地点切换和缓存。需要新地点时，由主持批准地点及边界，再生成候选图、审核、绑定版本。生成失败可继续用旧背景跑团。图片是表现层，不能依据画面里偶然出现的门自动增加可探索房间。

## 12. 真实行为、超时与状态一致性

每个行动绑定固定编号，并保存它依据的角色卡／场景版本。主持推进阶段后，尚未完成的旧版本草稿需要重新核对；不能让晚到回复继续描述已经取消的行为。

投骰与扣状态不能按普通查询处理。刷新页面只重新获取同一行动状态，不自动重掷。若请求超时、无法确定检定服务是否已经执行，则标记“结果不确定”，由主持处理；不以“重试”名义偷偷产生第二次骰点。

“我打算打开门”是提案；“已打开门”必须有批准与状态提交依据。状态写入成功前，AI 不能先对外宣布完成。暂停、断线会停止新任务并取消未发送草稿，但已经确认的骰点与事件不会因为取消而抹除。

## 13. 日志设计：一轮看懂，细节可追

公开日志按行动／发言轮次汇总，用整行横线分隔。ASR 高频片段、心跳与重复轮询合并成摘要。结构化审计保留细节；主持机密进入独立受限视图，不混入玩家导出文件。

每轮至少能看见：

- 哪些插件及功能开启，谁在什么场景版本下行动。
- 模型获得哪些公开信息与记忆来源；不记录私有内部思维链。
- 提出什么行为，谁批准了什么检定，实际工具、输入、结果和耗时。
- 骰点、规则版本、难度、奖惩骰与成功等级；状态变化前后值。
- 最终发言、表情实际反馈、TTS 参数及成功／失败状态。
- 取消、拒绝、冲突、超时和结果不确定等情况。

下面是模拟格式，没有执行真实检定或模型调用：

```text
------------------------------------------------------------------------
行动 A012｜故机｜办公室｜房间版本 28
功能：跑团插件开；自主讨论开；故机语音关；Live2D 表情开
观察：公开现场 E041；相关经历 M008；未提供主持机密
提案：检查桌上的文件，寻找来访记录
批准：主持甲；侦查 70；普通难度；无奖惩骰
工具：BCDice／COC7；开始 20:01:02.100；结束 20:01:02.180
模拟结果：23／70；困难成功
裁决：主持批准公开线索 C003；事实版本 28→29
记忆：新增“故机在文件中发现已公开的来访记录”，来源 E042
表现：thinking 启动成功；答复显示成功；语音关闭，未合成
最终发言：这里有一份来访记录，我们可以先核对这个名字
------------------------------------------------------------------------
```

日志中的“模拟结果”在真正运行时替换成可追溯的实际结果。未获批准、未命中、未播放不能写成成功；密钥不进入记录。模型用量按角色、用途和战役统计，区分输入、缓存与输出。

## 14. 开发顺序与验收门槛

### 阶段 A：选型接入验证，先不迁移正式局

验证两台电脑同版本 MapTool 联机、两位主持身份、可信宏调用连接服务，以及 BCDice 的固定版本接口。建立两张测试调查员卡，由真人 KP 完成一次“提案→批准→检定→记录→盘面同步”。此阶段不接入 AI KP。

盘面接入必须验证双向数据：服务能向 MapTool 提供批准状态，MapTool 也能提供带版本的位置与按调查员过滤的可见对象。不能直接拿 GM 全地图或 GM 视角截图给玩家模型。如果无法可靠取得角色观察，首版由 KP 明确发布观察信息，并将自动地图观察标为未支持；若该限制不可接受，就调整平台。

同时验证秘密过滤和界面组合。若 MapTool 回写只能依赖难以接受的手动操作，或不能满足你对统一界面的要求，应在此阶段停下来调整平台，不继续堆功能。

### 阶段 B：可以进行一段 COC 调查

接入两台 MaiBot、自由讨论与发言协调、基础检定、SAN／HP 记录、线索公开及隔离记忆。继续由真人 KP 描述现场、批准检定并确认后果。先用原创的短场景或经你们选择且有使用权的材料验证，不擅自选定正式模组。

验收：两个角色讨论后能提出合法行动；一次失败不会无限重掷；主持裁决改变后续记忆和回复；重启能恢复；双方不会看到对方未公开的私人线索。

### 阶段 C：舞台、语音与编辑体验

完成气泡、聊天可读性、每角色表情映射、语音开关、场景导入及故事编辑入口。两个观众同时测试，不以本机单浏览器成功代替异地验收。

### 阶段 D：接入 AI KP 测试，再按正式模组补规则

真人 KP 闭环通过后，增加 AI KP 适配器。先让它旁观并生成不对外发布的主持草案，比较其选用技能、难度、线索范围及状态修改与真人裁决的差异；再进入真人确认后发布的辅助主持模式。最后在独立短测试局中验证 AI KP 主持、两位真人监督接管的模式。

AI KP 可读取获授权的主持资料和规则索引；两个调查员只获得被公开的结果。AI KP 不能自行捏造骰点，实际检定仍经过同一引擎；人物卡与世界状态仍经同一提交接口保存。接管时暂停待发送内容，避免真人与 AI KP 同时发出冲突裁决。

依据正式模组需要，逐步补近战、射击、成长或追逐，明确每项自动化范围。自动主持的启用条件单独审核，不与“接入了 COC7 骰子”一起默认开放。

### 必须执行的测试清单

| 测试 | 通过标准 |
| --- | --- |
| 规则边界 | 固定测试骰序覆盖成功等级边界、奖惩骰和大成功／大失败，不靠随机运行一次判断 |
| 重复提交／断网 | 相同行动不会重复掷骰、重复扣 SAN 或重复发言；不确定状态明确显示 |
| 两位主持冲突 | 同时裁决有冲突提示，不覆盖已提交结果 |
| 调查员权限 | 玩家请求拿不到全模组、暗骰和另一角色私人内容 |
| 多人说话 | 主持讲话时无机器人抢话；同伴输出有序；讨论能结束 |
| 记忆隔离 | QQ／日常 Live2D／其他战役／旧分支资料不会误入当前角色 |
| Live2D | 两种模型分别测试存在与缺失资源；实际失败如实显示 |
| 语音 | 双观众都能播放；单角色关闭有效；TTS 故障不阻塞文字 |
| 时延 | 实测从接受输入到第一反馈、第一文字、第一段语音的时间，分别记录 |
| 旧功能回归 | QQ 群聊／私聊与个人 Live2D 可独立使用；不开跑团插件时不新增跑团调用 |
| 存档与回档 | 角色卡、事实、记忆和任务一致恢复；原审计保留 |
| 同伴安装 | 新目录和可配置地址能运行，无个人绝对路径、有效密钥或本机专属表情依赖 |

这些都是待实施后的验收要求。本轮没有运行上述集成测试。

## 15. 费用、交付与当前不足

### 费用控制

推荐路线的软件许可费可为零，模型、TTS、图片、联网或托管费用另算。角色模型只在需要决策或发言时调用，持续观察先合并事件；检定、排队和数值更新由程序处理，不再额外问一次大模型。复用场景图片，按角色可见范围缩小上下文，避免把完整模组和全部旧记录每轮重发。

不通过全局削低最终输出上限、关闭角色学习，或改变私聊回复路径来节约跑团费用。用量限额与暂停范围单独展示，由你们决定。

7. 免费软件不意味着开发维护成本为零；如果接入原型暴露出太多手动步骤，需要重新选型。
